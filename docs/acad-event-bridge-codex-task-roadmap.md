# Краткий roadmap реализации AutoCAD event bridge

Принцип работы с планом:

- идти строго сверху вниз;
- **один пункт = одна задача для Codex**;
- не объединять соседние пункты, пока текущий не доведён до рабочего состояния;
- после каждого пункта делать короткую ручную проверку.

---

## MVP

### [x] 1. Зафиксировать baseline текущего `acad-cmd`
**Что сделать:** добавить короткий smoke-checklist для текущего поведения `send_command`, `run_lisp`, `get_status`, `LOGFILEMODE` и убедиться, что всё работает до начала изменений.

**Готово, когда:** есть понятный baseline, и после каждого следующего шага можно сравнить поведение с исходным.

### [x] 2. Добавить feature flag для нового канала
**Что сделать:** в Python-слое добавить флаг `event_bridge_enabled`, по умолчанию не меняющий текущее поведение сервера.

**Готово, когда:** сервер полностью работает по старой схеме при выключенном флаге.

### [x] 3. Создать skeleton проекта `AcadEventBridge`
**Что сделать:** создать `plugins/AcadEventBridge`, `csproj`, `EntryPoint.cs`, пустой `BridgeHost`, базовую структуру файлов из спецификации.

**Готово, когда:** DLL собирается и загружается через `NETLOAD` без ошибок.

### [x] 4. Реализовать `PipeServer` и сообщение `hello`
**Что сделать:** создать named pipe `\\.\pipe\acad-event-bridge-<pid>`, поднять сервер внутри плагина и отправлять `hello` после подключения клиента.

**Готово, когда:** внешний тестовый Python-скрипт может подключиться к pipe и получить `hello`.

### [x] 5. Добавить `heartbeat` и базовые DTO
**Что сделать:** реализовать `EventModels.cs`, сериализацию NDJSON и периодическое сообщение `heartbeat`.

**Готово, когда:** после `hello` клиент стабильно получает heartbeat с `seq`, `ts`, `busy`, `queue_depth`.

### [x] 6. Добавить `EventQueue` и `StateTracker`
**Что сделать:** сделать bounded queue, счётчик `seq`, поля `busy`, `command_depth`, `lisp_depth`, `active_doc_id`, `dropped_count`.

**Готово, когда:** heartbeat заполняется из `StateTracker`, а очередь защищает от зависания writer-потока.

### [x] 7. Подписать `DocumentCollection` события
**Что сделать:** реализовать `EventRegistrar` и публикацию `document_created`, `document_activated`, `document_destroyed`.

**Готово, когда:** открытие, переключение и закрытие DWG видно в pipe как структурированные события.

### [x] 8. Подписать command lifecycle события
**Что сделать:** добавить `CommandWillStart`, `CommandEnded`, `CommandCancelled`, `CommandFailed`.

**Готово, когда:** обычная команда AutoCAD даёт событие старта и одно завершающее событие.

### [x] 9. Подписать LISP и вспомогательные события
**Что сделать:** добавить `LispWillStart`, `LispEnded`, `LispCancelled`, `UnknownCommand`, `ImpliedSelectionChanged`.

**Готово, когда:** запуск LISP и изменение implied selection отражаются в event stream.

### [x] 10. Сделать Python-клиент `bridge_plugin_client.py`
**Что сделать:** реализовать подключение к pipe, чтение NDJSON, поток/таск чтения, разбор `hello` и `heartbeat`.

**Готово, когда:** Python-процесс видит живой bridge и умеет хранить его базовое состояние.

### [x] 11. Сделать `event_state.py`
**Что сделать:** хранить `last_seq`, `busy`, `command_depth`, `lisp_depth`, `active_doc_id`, последние command-события и время heartbeat.

**Готово, когда:** состояние bridge можно читать из одного объекта без прямого разбора сырых JSON в бизнес-логике.

### [x] 12. Подключить bridge к `get_status()`
**Что сделать:** добавить lazy connect по PID AutoCAD, `get_pid()`, `get_pipe_name()` и блок `event_bridge` в `get_status()`.

**Готово, когда:** `get_status()` показывает `available/connected/plugin_version/last_seq/last_heartbeat`.

### [x] 13. Реализовать `command_waiter.py`
**Что сделать:** сделать отдельный модуль ожидания completion: сначала по event stream, потом fallback на `wait_for_idle()`.

**Готово, когда:** waiter умеет дождаться `command_ended`, `command_cancelled`, `command_failed`, `lisp_ended`, `lisp_cancelled`.

### [x] 14. Интегрировать waiter в `send_command()`
**Что сделать:** после `SendCommand` ждать completion через `CommandWaiter`; если bridge недоступен — сразу использовать старый путь.

**Готово, когда:** `send_command(wait=true)` работает и с bridge, и без bridge, без поломки текущего API.

### [x] 15. Интегрировать waiter в `run_lisp()` и `load_lisp_file()`
**Что сделать:** перевести LISP-вызовы на ту же схему ожидания событий, сохранив текущие fallback-механизмы.

**Готово, когда:** LISP-сценарии завершаются корректно и не требуют отдельной логики ожидания вне bridge.

### [x] 16. Добавить hardening для разрывов и перегрузки
**Что сделать:** reconnect, heartbeat timeout, обработку disconnect, `dropped_count`, безопасную деградацию обратно на COM/`LOGFILEMODE`.

**Готово, когда:** отключение pipe или падение плагина не ломает сервер и не требует его перезапуска.

### [x] 17. Провести финальный smoke test MVP
**Что сделать:** проверить сценарии: без плагина, с `NETLOAD`, простая команда, LISP, переключение документов, разрыв pipe.

**Готово, когда:** все сценарии проходят, а сервер в любом режиме остаётся работоспособным.

## После MVP

### 18. Добавить opt-in object events
**Что сделать:** под feature flag включить `object_appended`, `object_modified`, `object_erased`.

**Готово, когда:** object-level события можно включить отдельно, не зашумляя стандартный режим.

### 19. Сделать автозагрузку плагина
**Что сделать:** выбрать один способ доставки: app bundle, installer или стабильный scripted load.

**Готово, когда:** пользователю не нужно вручную делать `NETLOAD` на каждом рабочем месте.

### 20. Добавить request/response поверх pipe
**Что сделать:** расширить протокол двусторонними сообщениями для диагностических и служебных запросов.

**Готово, когда:** Python может не только слушать события, но и получать структурированные ответы от плагина.

### 21. Исследовать отказ от COM для части команд
**Что сделать:** проверить, какие команды можно безопасно запускать через сам плагин, оставив COM только как fallback.

**Готово, когда:** есть отдельное решение, стоит ли делать phase 2 с уменьшением роли COM.
